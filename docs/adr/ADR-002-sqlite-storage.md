# ADR-002. Одна база SQLite (WAL), спільна для сервера й обробника

- **Статус:** прийнято 10.11.2026; переглянуто для v2.0 20.11.2026 — **чинне**
- **Задачі:** Sprint 4 — B1; v2.0 — C6, D3; код: `web/db.py`, `web/models.py`

## Контекст

Вебсистема зберігає заявки, файли, історію статусів, проєкти, а з v2.0 — користувачів і журнал дій. Записують
у базу два процеси (сервер і обробник, ADR-001). Система навчальна: кілька операторів, сотні–тисячі заявок,
локальний запуск без адміністрування сервера БД. Вимога лаби — модульний застосунок із локальною базою, без
платних сервісів.

## Розглянуті варіанти

1. **PostgreSQL.** Плюс: справжня конкурентність, транзакції рівня рядка, готовність до масштабу.
   Мінус: окремий сервер, якого немає в чистому середовищі; передавання й CI ускладнюються (контейнер або
   встановлення), а виграш на нашому навантаженні не відчутний.
2. **Файли JSON на кожну заявку.** Плюс: нуль залежностей. Мінус: немає транзакцій і запитів — фільтри дошки,
   статистика, захист від подвійного рішення довелося б писати вручну; два процеси пишуть у ті самі файли.
3. **SQLite через SQLAlchemy, режим WAL.** Плюс: один файл `data/web.db`, нічого не встановлювати; транзакції
   й SQL; WAL дозволяє читати під час запису; SQLAlchemy лишає можливість перейти на PostgreSQL зміною URL.
   Мінус: один записувач одночасно; блокування на рівні бази.

## Рішення

Варіант 3. `PRAGMA journal_mode=WAL` і `busy_timeout=30000`: читачі не блокують записувача, а записувач чекає
до 30 с замість помилки. Шлях до папки даних задається `DAMAGE_WEB_DATA` (за замовчуванням `data/`); усі
шляхи до файлів заявок відносно неї.

## Наслідки

**Позитивні**
- Чисте середовище піднімається за `uv sync` без сервера БД — це перевірено передаванням (D8).
- Резервна копія — консистентна копія одного файлу через SQLite backup API, навіть під час роботи сервера (D3).
- Тести створюють окрему тимчасову базу на кожен запуск.

**Негативні**
- Записи серіалізуються: при багатьох одночасних записувачах будуть очікування (не наш випадок).
- Помилка в шляху до папки даних мовчки створювала нову порожню базу — причина навчального інциденту
  20.11.2026; закрито перевіркою при старті (D6, PR #4).
- Міграції схеми робимо самі (ADR-006), бо SQLite обмежено підтримує `ALTER TABLE`.

## Умова перегляду

Більше ~5 одночасних операторів із помітними очікуваннями блокувань, розгортання на кількох машинах або
потреба в реплікації — тоді PostgreSQL (SQLAlchemy вже ізолює більшість коду від СУБД).

## Перегляд для v2.0 (20.11.2026)

v2.0 додала таблиці `app_user`, `audit_event`, `schema_version` і три стовпці. Кількість записувачів не
змінилася (сервер + один обробник), журнал дій пишеться в тій самій транзакції, що й дія. Виміряно: дошка
з 1000 заявками відповідає за p95 = 133,5 мс (поріг 1 с). **Рішення чинне.**
